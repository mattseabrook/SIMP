# Threading and GPU work

The Win32 window/input thread and Vulkan submission/presentation thread are separate, named threads. Both request `THREAD_PRIORITY_ABOVE_NORMAL`; CPU workers run at normal priority. Priority influences Windows scheduling rather than reserving a CPU core or guaranteeing a latency deadline. See [Microsoft's scheduling documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities).

The window thread handles native messages, lightweight editor state, hit testing and frame geometry. It posts owned render commands and immutable frame packets. The render thread owns the device, queues, resources, synchronization and swapchain. It may wait for a GPU fence or presentation without stopping native input. Pending UI frames coalesce to the latest geometry. Paint/upload commands keep their order; generation identifiers stop frames from a previous document from being combined with a newly replaced texture. Minimized and idle rendering sleeps.

A shared worker pool handles opening/decoding, new-canvas/cel initialization and duplication, exact-color inventory, native saves and PNG export. It uses at most eight normal-priority workers to bound scheduling/memory pressure. Large memory operations share ranges; callers participate so nested parallel operations cannot deadlock waiting for queued helpers. Small ranges run inline. Save/export jobs capture immutable, shared pixel snapshots. Editing detaches storage if a reader still owns it. Completion callbacks run on the window thread, outside native dialog callbacks; document epochs/revisions and open tickets reject obsolete results. PNG jobs initialize their own COM apartment and encoder. Completed history entries go to a separate serial I/O queue, so disk writes do not occupy decoding or palette workers. Closing/replacing a document cancels obsolete queued journal writes; each job owns the journal lifetime until it finishes.

AVX2 is selected after CPU and OS register-state checks. The executable retains an SSE2 path for other x64 processors. Fills and RGBA/BGRA conversion handle unaligned pointers and scalar tails. The color inventory uses an exact RGB bitset (two MiB), parallel scanning, and compact three-byte palette entries; tiny images use a small sorted list. Alpha variations do not create duplicate paint colors. Every stored RGB value counts across all cels, including hidden cels and RGB under transparent pixels. Palette revisions track pixel/structural changes separately from guide and visibility changes, preventing unrelated edits from invalidating an in-flight scan.

## What the GPU terms mean

| Term | Meaning for this editor |
| --- | --- |
| Graphics shaders | GPU programs draw the workspace, text, controls, rulers and guide highlights. |
| GPGPU / compute shaders | General pixel/math operations executed on the GPU. Brush and cell painting use a Vulkan compute shader and storage image when the required capabilities are present. |
| CUDA | NVIDIA's alternative compute platform. No CUDA runtime or interop copies are needed for the current Vulkan compute path. |
| Tensor cores | Specialized matrix/AI hardware. A future AI operation needs an appropriate model and implementation to use them. |
| RT cores | Specialized ray-tracing hardware. Future ray-based features could use them; ordinary 2D brush and cell painting does not require ray traversal. |

Vulkan storage images allow shader writes directly into image storage; the implementation checks BGRA storage-image support, writes without a declared image format, the optional format-feature-flags extension, and compute support on the graphics queue before enabling this path. See the [Khronos storage-image guide](https://docs.vulkan.org/guide/latest/storage_image_and_texel_buffers.html). NVIDIA documents the RTX 4070 family's separate compute, Tensor and RT hardware in its [architecture overview](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4070-family/). Hardware features should be enabled for operations that benefit from them, with results and timings checked on the actual adapter.

## Current limits and next measurements

Straight brush runs coalesce into rectangles, and adjacent same-color stamps skip already covered strips to avoid repainting large square overlaps. Brush and cell tools share the SIMD CPU fill, history capture, and Vulkan compute/upload paths. Compute painting updates the device-local display image without a pixel upload for each fill. A CPU image is still updated for exact saves and session undo. Decoders and encoders remain CPU codecs. Touched-tile capture, CPU pixel edits, copy-on-write detachment, and undo/redo journal reads and application still run as part of window-thread editing. Normal history commits queue their journal writes asynchronously, but an immediate undo can wait for the queued record. These remaining costs should be profiled before replacing the reference-image/history architecture with GPU-resident tiles and asynchronous readback. GPU color-inventory reduction and GPU filters are future work; this release does not claim CUDA, Tensor, RT, or GPU codec acceleration.

Visible cels use separate sampled Vulkan textures and hardware source-over blending over a checkerboard in the UI render pass. Selection and visibility update metadata; structural stack changes rebuild textures on the render thread. Each queued upload/paint command remembers its target cel. PNG and native compatibility-preview compositing stays on CPU workers, and original source pixels remain in separate cel records.

Automated tests execute the graphics and compute modules on a headless software Vulkan ICD and compare bytes with a CPU reference. Software Vulkan is never accepted by the editor's device selector. Linux sanitizer checks cover document handling, CPU/SIMD work, nested parallel jobs, and workspace geometry. They cannot establish Windows message latency, swapchain behavior, NVIDIA hybrid selection, or RTX 4070 performance.

On the target Windows system, measure input-to-present latency, frame CPU/GPU time, large-image open/save time, peak memory and stroke/undo time at fit and ORIGINAL zoom. Include a many-color image, alpha data, large cells, concurrent save/edit, repeated resize and rapid document replacement. Compare release builds with the same data and driver settings. No best-in-class or speedup ranking has been established yet.

The executable is approximately 6.2 MiB after replacing 141 embedded PNG resources (about 68 MiB) with one H.264/MP4 (about 4.6 MiB), plus the original first-frame fallback PNG. The build uses libx264 CRF 12 with animation tuning, High profile, 4:2:0 chroma and BT.709 tags. The perceptually lossless target is a visual quality choice; document pixels remain lossless. Build assets are hashed and cached, and source bitmaps are never rewritten. A source-versus-encode SSIM check in the same BT.709/4:2:0 domain measured 0.996762 over 141 frames (worst frame 0.995972); that metric does not include the chroma-subsampling loss and does not replace visual inspection.

The splash reads the embedded MP4 through Windows' [Media Foundation source reader](https://learn.microsoft.com/en-us/windows/win32/medfound/processing-media-data-with-the-source-reader), using [advanced video processing](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-enable-advanced-video-processing) to obtain RGB32 on its own COM thread. Playback keeps at most three queued decoded frames rather than caching the complete animation. Media DLLs are optional, process-local loads; unavailable codecs leave the poster visible. The compressed resource is copied once into a Windows memory stream, not a temporary file. RGB32 frames are copied into the native splash back buffer; no D3D/Vulkan zero-copy decoding is claimed by this implementation. Actual Windows decoder latency and playback pacing need target-machine measurement.

Splash drop shadows are generated once at startup from text coverage and original logo alpha (not logo brightness). A one-pixel spread and separable Gaussian kernels with sigma 16/6, at lower opacity, produce a broad smooth fade, offset two pixels right and four down. Artwork is inset enough to contain that fade; hard text outlines are removed. CPU workers share startup filtering. Playback alpha-blends one cached premultiplied black bitmap before drawing the sharp text and logos; no blur or shadow allocations run per frame.
